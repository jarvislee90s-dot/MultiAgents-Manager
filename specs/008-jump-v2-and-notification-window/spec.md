# 功能规格说明：跳转 v2（四层降级）+ 自定义通知浮窗

**功能分支**：`008-jump-v2-and-notification-window`

**创建日期**：2026-08-24

**状态**：草稿

**输入**：Windows 窗口跳转第一版（spec 007）实测反馈与实机取证——跳转命中"Z 序抽奖"（Windows Terminal 单进程 7 窗口无法区分；explorer.exe 混入祖先链导致跳到文件资源管理器；ChatGPT 置前失败仅表现为看板失焦）；通知弹窗借用系统 WinRT toast 且发送者身份显示为 PowerShell。经多轮设计讨论确认四层降级定位策略与独立通知浮窗方案。

## 用户场景与测试

### 用户故事 1 — 跳转准确命中目标窗口（优先级: P1）

用户在看板里点击某张会话卡片，无论开了多少个终端窗口、多少个会话，聚焦的必须是那张卡片对应的窗口。

**优先级理由**：跳转不准等于功能不可用，且当前行为（跳到随机窗口）比不跳更干扰。

**独立测试**：同一项目开两个 claude 会话（两个 WT 窗口）+ 另一个项目的 codex + 一个空的 PowerShell 窗口，分别点击四张卡片，每次聚焦均正确。

**验收场景**：

1. **给定** 三个 WT 终端窗口分别跑 claude/codex/opencode（不同项目），**当** 逐一点击卡片，**则** 各自聚焦到对应窗口
2. **给定** 同一项目、同一工具开了两个会话（标题启发无法区分），**当** 点击其中一张卡片，**则** 聚焦到正确的那个窗口（marker 或内容匹配命中；均 miss 时弹窗口选择器，用户选择后聚焦）
3. **给定** 多个文件资源管理器窗口打开且 Z 序靠前，**当** 点击 VS Code / ChatGPT / 终端卡片，**则** 绝不聚焦到资源管理器（explorer 在黑名单）
4. **给定** ChatGPT 桌面版在后台或最小化，**当** 点击 Codex App 卡片，**则** ChatGPT 窗口恢复并置前
5. **给定** VS Code 多窗口、目标会话在其中一个的集成终端里，**当** 点击卡片，**则** 聚焦到该窗口（VS Code 每窗口独立主进程）
6. **给定** 目标窗口已最小化，**当** 点击卡片，**则** 恢复并置前
7. **给定** 终端已关闭（进程退出），**当** 点击卡片，**则** toast 提示"未找到可聚焦的窗口"，不崩溃不静默

### 用户故事 2 — 卡片标识与窗口可对读（优先级: P3）

用户在窗口标题栏看到 `MAM:xxxxxxxx` 时，能立刻在看板上找到对应卡片；反之亦然。

**验收场景**：

1. **给定** hook 注入生效的会话，**当** 查看终端窗口标题栏与看板卡片，**则** 两者显示相同的 8 位 session ID 前缀（卡片显示由 12 位改为 8 位，与 marker 一致）

### 用户故事 3 — 任务完成时的自定义通知浮窗（优先级: P1）

任务状态变化时（进入运行、结束等待），应用右下角浮现自有的通知卡片（非系统 toast、非 PowerShell 名义）：置顶显示但不抢键盘焦点、不打断正在进行的输入；数秒后自动滑出消失，鼠标悬停时保留；点击通知卡片直接跳转对应会话终端。

**优先级理由**：用户明确要求的自有通知形态，替代借用系统身份的 WinRT toast。

**独立测试**：后台跑一个 claude 任务，期间在别的窗口打字；任务完成时右下角浮出通知卡（打字不被打断），点击卡片聚焦到该终端。

**验收场景**：

1. **给定** 应用在后台（主窗口最小化或缩至托盘），**当** 某会话状态变化触发通知，**则** 右下角浮现应用自定义通知卡片，显示工具、项目名、状态色、最新消息预览
2. **给定** 用户正在其他窗口打字，**当** 通知浮现，**则** 键盘焦点不被夺取（通知窗口不激活）
3. **给定** 通知已显示约 6 秒且鼠标未悬停，**当** 到时，**则** 通知自动消失；**给定** 鼠标悬停在通知上，**则** 保持显示直至移开
4. **给定** 多个会话先后触发通知，**当** 第二、三条到来，**则** 通知卡片向上堆叠（最多 3 条，超出顶替最旧）
5. **给定** 通知卡片可见，**当** 点击它，**则** 关闭该通知并执行对应会话的跳转（走用户故事 1 的四层降级）
6. **给定** 设置中"使用系统通知"开关关闭（默认），**当** 状态变化，**则** 仅弹自定义浮窗，不出现系统 toast
7. **给定** 设置中"使用系统通知"开关打开，**当** 状态变化，**则** 走原系统通知通道（保留现状能力）
8. **给定** 通知提示音开启（现有配置），**当** 通知触发，**则** 声音行为与现状一致

### 用户故事 4 — macOS 无回归（优先级: P1）

**验收场景**：CLI 卡片跳转走现有 TTY 链路行为不变；通知浮窗为全平台能力（macOS 同样可用自定义浮窗，不引入平台特判）。

## 设计

### A. 跳转 v2 — 四层降级定位（重构 `window/win32.rs`）

聚焦目标解析改为按层降级，每层产生"候选窗口集合"，逐层收敛：

**第 1 层（确定性）：近祖优先 + shell 黑名单。**
祖先链按距离从近到远排序扫描（替代第一版的"整条链 PID 集合 + Z 序任取"）；维护不可作为跳转宿主的进程黑名单（`explorer.exe`、`sihost.exe`、`svchost.exe`、`ctfmon.exe` 等系统 shell/服务进程）；第一个不在黑名单且拥有可见顶层窗口的祖先进程，其窗口为候选集。ChatGPT/VS Code/独立终端由此精确命中。

**第 2 层（高命中）：窗口标题启发。**
当第 1 层候选集含多个窗口（WT 单进程多窗口场景），按标题打分：标题包含工具名关键词（"Claude"/"codex"/"opencode" 等）加分、包含项目目录名加分；取最高分。标题经 `GetWindowTextW` 获取。

**第 3a 层（精确匹配，spike 先行）：hook 注入 `MAM:<session-id 前 8 位>` 标题 marker。**
MAM 已为 Claude/Codex 安装管理 hook（OpenCode/OpenClaw 无 hook 机制，不适用）。hook 脚本在事件触发（含 Stop/任务结束）时向**控制台输出设备**（Windows `CONOUT$`）写 OSC 转义序列设置终端标题为携带 8 位 session ID 前缀的 marker（如 `MAM:1ba8e2f7`，附加在原标题后）。聚焦侧直接按标题精确匹配。要点：
- 写 `CONOUT$` 而非 stdout（工具会截获 hook 的 stdout）
- `Stop` 事件时机与用户点卡片时机天然对齐
- 需 spike 实测：hook 子进程在 ConPTY 下写 CONOUT$ 能否稳定送达标题、工具自身标题重写的覆盖频率；**spike 结论不成立则本层降级为不启用，第 3b 层升为主力**
- hook 需要拿到当前 session ID（从工具传入 hook 的参数/环境变量中读取，各工具的 hook 入参格式在实现时核实）

**第 3b 层（内容匹配）：UIA 文本匹配。**
经 UI Automation（屏幕阅读器通道）读取候选窗口终端的可见文本，与看板会话的 `lastMessage` 尾部片段（空白归一化后取尾部约 40 字符）做子串匹配。复用看板现有提取函数的输出（`Session.lastMessage`）作为参照文本，不另建提取逻辑；窗口侧为渲染文本，仅做空白归一化与尾部子串判断，不做更重的模糊算法。读取失败/超时（单窗口上限约 200ms）视为 miss。

**第 4 层（兜底，永远正确）：窗口选择器。**
前三层全部 miss 或仍有多窗口歧义时，弹出选择浮窗：列出候选窗口的标题与所属进程，用户点选后聚焦。候选为空则报"未找到可聚焦的窗口"。

**聚焦动作增强**：最小化先 `SW_RESTORE`；`SetForegroundWindow` 失败时降级链：`SwitchToThisWindow` → `AttachThreadInput` 挂接前台线程后重试 → 报错。

**macOS/Linux**：现有 cfg 分发结构不变，本 spec 仅改 `#[cfg(windows)]` 分支内部实现。

### B. 卡片显示前缀统一（8 位）

Claude/Codex 卡片标题的 session ID 显示由前 12 位改为前 8 位（`parser.rs` 两处 `min(12)` → `min(8)`），与 marker 长度一致，实现"窗口标题栏 `MAM:xxxxxxxx` ↔ 看板卡片 `xxxxxxxx` 可对读"。

### C. 自定义通知浮窗（独立 WebviewWindow）

**窗口形态**：独立无边框窗口（label 轮转复用，如 `notification-0..2`），尺寸约 360×120，初始隐藏；通知时定位主显示器右下角（预留系统边距）、`always_on_top(true)`、`skip_taskbar`、**`focusable(false)`（Windows 即 WS_EX_NOACTIVATE：置顶显示但不激活、不夺键盘焦点，鼠标点击仍可响应）**、透明背景。加载专用路由（如 `/notification`），与主窗口共享前端代码与状态。

**触发链路**：`useNotification` 检测状态变化（现有逻辑不变，含 5 秒去重）→ 发出 Tauri 事件 `notification:new`（载荷：agentType、项目名、状态色、lastMessage 预览、pid、sessionId）→ 通知窗口（或 Rust 侧窗口管理器）接管显示；提示音沿用现有 `playSoundForStatus`。

**生命周期**：显示后 6 秒自动隐藏；`mouseenter` 取消计时、`mouseleave` 重新计时；点击卡片 → 隐藏自身 + `invoke("focus_session", { pid })`（走四层降级）。多条堆叠：3 个窗口槽位轮转，超出顶替最旧；窗口隐藏而非销毁（避免反复创建开销）。

**设置项**：现有通知设置中新增"使用系统通知"开关（默认关）。关闭（默认）= 仅自定义浮窗；打开 = 走现有 `tauri-plugin-notification` 通道。现有提示音开关与行为不变。

**范围界定**：系统通知的 AUMID 修复（让系统 toast 以应用身份显示）不在本 spec——默认通道已切换为自定义浮窗，系统通道仅作可选保留。

### D. 明确不做（YAGNI）

- Windows Terminal 标签页级定位（若 3a spike 成立，marker 已覆盖多标签歧义的核心场景）
- Linux/Wayland 跳转
- macOS 的 ChatGPT 窗口聚焦
- 通知浮窗的多显示器分发、勿扰时段等高级功能
- 对 OpenCode/OpenClaw 的 hook 机制补齐

## 错误处理

- 各层解析失败一律向下降级，不 panic；全链 miss 走第 4 层或明确报错
- UIA 读取设超时与异常捕获，COM 初始化失败时该层整体跳过
- hook 注入失败（脚本缺失/参数不匹配）静默降级，不影响工具本身的 hook 行为
- 通知窗口创建失败时降级为系统 toast（记录日志），保证通知不丢

## 测试策略

- 纯逻辑单测：祖先链近远排序与黑名单过滤（闭包注入进程树）、标题打分函数、空白归一化与尾部子串匹配函数、marker 串生成与解析
- spike 报告：CONOUT$ 标题注入在真实 Claude/Codex 会话中的稳定性（手动验证 + 结论记录，决定 3a 去留）
- 人工验证：用户故事 1/2/3 的全部验收场景实机执行（含"同项目双会话"与"资源管理器干扰"两个此前失败场景）
- 门禁：cargo test / clippy / fmt、pnpm lint / build 全过；macOS 侧回归由 CI 与既有平台条件测试保障
