# 功能规格说明：i18n 全量清理

**功能分支**：`009-i18n-full-coverage`

**创建日期**：2026-08-24

**状态**：草稿

**输入**：Windows 兼容性与跳转两轮修复后的用户反馈——切换界面语言后，主看板、资源管理（全部/按资源/按工具视图）、MCP 面板、设置页通知区等大量界面文字不跟随切换。前期排查结论：`src/i18n/locales/zh.json` 与 `en.json` 键集完全对齐（99/99，零缺失），根因是 **16 个组件文件硬编码中文字符串绕过了 i18n**（SessionCard.tsx 已在上一轮清理，不计入）。

## 用户场景与测试

### 用户故事 1 — 界面语言完整切换（优先级: P1）

用户在设置中切换中/英文后，**整个应用**的界面文字（首页看板、资源管理三视图、MCP 面板、预设组、设置页、弹窗与 toast、错误边界）都跟随切换，找不到"漏网"的硬编码文字。

**优先级理由**：语言切换是已发布功能，大面积不生效属于功能缺陷，且每处硬编码都在持续累积债。

**独立测试**：切换到 English 后，逐页巡检（首页、资源三视图、MCP、设置全部子页、触发一次错误边界页），无中文字符串残留（专有名词与用户内容除外）。

**验收场景**：

1. **给定** 界面语言为 English，**当** 巡检首页看板（含状态筛选、空状态、时间格式文案），**则** 全部为英文
2. **给定** 界面语言为 English，**当** 巡检资源管理三个视图（全部/按资源/按工具）与导入对话框，**则** 全部为英文
3. **给定** 界面语言为 English，**当** 巡检 MCP 面板与预设组界面，**则** 全部为英文
4. **给定** 界面语言为 English，**当** 巡检设置页全部子页（含通知、提示音、截图工具等），**则** 全部为英文
5. **给定** 触发组件错误（错误边界页），**当** 巡检错误提示文案，**则** 为英文
6. **给定** 切换回中文，**当** 巡检上述全部页面，**则** 全部为中文，与英文版语义一致
7. **给定** 任意语言，**当** 查看工具徽标（Claude/Codex/OpenCode/OpenClaw）、语言切换器中的语言名（"中文"/"English"），**则** 保持原样（专有名词/原生语言名不翻译）

### 用户故事 2 — 键集对齐进入门禁（优先级: P2）

新增或修改 i18n 键时，zh/en 两文件键集不一致应被自动拦截，防止未来再次出现"一种语言缺翻译"。

**验收场景**：

1. **给定** zh.json 与 en.json 键集一致，**当** 运行校验命令（`pnpm check:i18n`），**则** 退出码 0
2. **给定** 任一语言文件缺键或多键，**当** 运行校验命令，**则** 退出码非 0 并列出差异键
3. **给定** 校验命令纳入 `pnpm check`，**当** CI / 本地执行完整检查，**则** 键不一致会导致失败

## 设计

### 1. 全量审计（第一步，产出权威清单）

以脚本扫描 `src/` 下所有 `.tsx`/`.ts` 文件（排除 `src/i18n/` 自身、`tauri-mock.ts`、测试文件），检出 JSX 文本节点、字符串字面量、模板字符串、toast/title/placeholder 属性中的中文（含中文标点）。输出文件级清单，作为后续任务的执行范围。已知在列的文件（以审计结果为准）：McpManager、ExtensionList、SessionGrid、ResourceByKindView、ResourceByToolView、ImportDialog、ScreenshotTool、PageErrorBoundary、ErrorBoundary 等 16 个；明确排除：language-toggle.tsx（语言原生名，属有意保留）、AGENT_BADGE 等专有名词。

### 2. 逐文件接入 i18n

每个文件：在 `zh.json`/`en.json` 中按现有命名空间惯例新增键（复用已有顶层命名空间的进入对应子级，无对应的新建，命名沿用现有 `camelCase` 风格）；组件内 `useTranslation` 取词替换硬编码字符串；含插值的文案使用 i18next 插值（`{{error}}` 等）而非字符串拼接。**两语言文件同步修改，键集始终对齐。**

### 3. 校验脚本与门禁

新增 `scripts/check-i18n.mjs`（Node，零新依赖）：加载两语言 JSON，递归展开键路径比较集合，输出缺失/多余键并以非零码退出。注册为 `pnpm check:i18n`，并加入 `pnpm check` 组合命令。i18next 支持嵌套键读取，无需引入类型生成等重方案。

### 4. 明确不做（YAGNI）

- 不引入 i18next TypeScript 类型化键（`react.i18next.d.ts` 自动生成）——与本次目标无关，未来按需
- 不翻译 AGENTS.md/文档/README（文档体系另有 spec）
- 不处理 Rust 后端的中文错误消息（`Result<(), String>` 里的中文）——属后端 IPC 文案，单独议题
- 不新增第三种语言

## 错误处理

- 插值缺失/多余参数：i18next 默认渲染键名，巡检场景覆盖
- 动态拼接的文案（如 `跳转失败: ${e}` 模式）统一改为插值键，消除拼接残留

## 测试策略

- `pnpm check:i18n` 校验脚本对"一致/缺键/多键"三种输入的行为（脚本自带最小自测或以构造样例验证）
- `pnpm lint` / `pnpm build` 全过
- 人工巡检：用户故事 1 的 7 个验收场景（两种语言各巡检一遍）
