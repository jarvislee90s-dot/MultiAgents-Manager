## 1. 目标与范围

二期交付一条主线：**手机给特定会话发消息，agent 真实收到并处理，桌面自然可见，不打断运行中的会话**。按交付顺序展开为五块：

1. **已开始的对话框（终端里的 TUI）**——终端注入引擎直达：macOS 三通道（tmux/iTerm2/Terminal.app）+ Windows 终端通道（D18），打字+回车语义，实时可见；
2. **等待批准的红卡**——手机一键应答（注入对应按键，D12 第二层）；
3. **未开窗的会话**——无头通道五家一次做齐（zcode/claude/codex/kimi/opencode），一次 turn + 回执；
4. **任务交接**——会话摘要导出 HANDOFF.md（F2.7）；
5. **触达补全（D15/D17 移入项）**——推送网关（Bark/ntfy）+ APK 壳收尾 + manualChunks 分包。

**二期不做（边界，非选项）**：切模型/切模式（F3.1 结构化选择器 UI 属三期；斜杠命令**文本**原样放行，见 W4）；会话管理操作；自动流转导入侧（ImportService 属三期 F3.7）；绕过各 harness 自身权限体系；keystroke/accessibility 正式功能（仅 W10 文档级应急预案，D7）。

**分期递进对位**：一期只读（已收官）→ 二期白名单消息（本册）→ 三期受控操控。每次里程碑扩权独立评审（宪法横切原则 1）。

## 2. 写通道总体架构

```
手机输入框（会话详情页，多行）
   │ POST /m/api/session-send（PIN 配对设备 cookie 过闸）
   ▼
注入路由表（会话宿主形态 → 通道决策 + 有头可见性预期）
   ├─ 终端注入引擎（tmux / iTerm2 / Terminal.app / Windows）→ 打字+回车，实时可见
   ├─ 无头通道（zcode / claude / codex / kimi / opencode）→ 子进程一次 turn，回执返回
   └─ 不可注入（WorkBuddy 黑盒 / dsh 待评 / APP 形态）→ 输入框禁用 + 原因说明
   ▼
状态门控队列（黄排队 / 可输入态逐条 flush / 单会话串行 / 可查可撤回）
   ▼
写审计表（SQLite：设备 / 时间 / 会话 / 通道 / 动作 / 内容摘要）→ 发送回执
```

## 3. 第一部分 · 发消息主线（W1–W5，对应宪法 F2.1/F2.2/F2.5/F2.6/F2.10）

### W1 · 终端注入引擎（macOS 三通道）

- **需求**：终端里已开的 TUI 会话收到手机消息——打字+回车语义，桌面终端实时可见。
- **输入**：注入请求（session_id、归一后文本、设备花名）；路由表解析出的宿主终端与定位键（tmux pane / tty）。
- **输出与效果（二期行为定死）**：
  - 三通道：tmux `send-keys -t <pane> -l --` + Enter（`-l` 字面量必需，杜绝 `:` 开头被解析为键名）；iTerm2 `write text`（先写文本再补回车，分两步可校验）；Terminal.app `do script ... in window`（转义反斜杠/引号）；
  - 消息标记：`[mobile <设备花名>] ` 前缀，桌面一眼可辨来源；
  - 纯文本语义：send-keys -l 与 write text 均按字面传递，不拼接 shell 元字符转义逻辑；不用 paste-buffer（TUI 粘贴确认行为语义随版本变）；
  - 定位复用 `window/` 既有链路（跳转功能同源），无新定位逻辑。
- **边界**：keystroke/accessibility 仅应急预案（W10/D7）；定位失败（终端已关闭/会话已死）返回明确失败回执，不入队重试。

### W2 · 状态门控队列

- **需求**：不打断正在运行的会话——黄状态消息排队，agent 空下来能收输入时自动放出。
- **输入**：注入请求 + 会话当前状态（SessionWatcher 提供）。
- **输出与效果**：
  - 黄（运行中）= 入队（SQLite 队列表，含设备花名/时间戳/内容）；
  - **会话回到「可输入态」即逐条 flush**。可输入态 = 红·等待（等批准/等输入）**或** 绿·完成/空闲——通俗说：agent 停下来把光标交回输入框的任何时刻（无论它是在等你批准，还是任务做完了）。宪法原文只写了「转红 flush」，但任务完成（转绿）时 agent 同样停在输入框前等下一条指令，若只在转红时放行，完成场景的排队消息会一直压着不发，所以要扩成两种状态都放（宪法口径的完整化，非冲突）；
  - 一次只放一条，发出后重新等待下一个可输入态 = 单会话串行（天然限速）；
  - 红·中断（写入者已死，终端里没人接消息）不 flush：队列挂起，移动端明示「会话已中断，消息保留」；
  - 移动端可查队列（排队中条目+序）可撤回未发；**「立即发送」插队（裁决 12）**：任一排队项可手动越过状态门即刻注入——运行中的 TUI 会把消息放进它自身的输入缓冲（Claude Code 官方支持运行中排队输入），各家运行中注入行为 = M7 实测确认项；「按最新内容发」= 撤回旧项 + 立即发送新项；队列持久化，MAM 重启不丢。
- **边界**：队列仅作用于终端注入通道（无头通道自身按 turn 串行，不入队）；flush 失败（终端消失）逐条降级为失败回执。

### W3 · 注入路由表

- **需求**：每个会话该走哪条通道，手机上一目了然。
- **输入**：会话的宿主形态（MAM 已区分 CLI/APP/终端类型与进程信息）。
- **输出与效果**：通道决策（tmux/iTerm2/Terminal/Windows/ZCode 无头/通用无头/不可注入）+ **有头可见性预期**（实时 / 刷新后 / 不可见）返回移动端展示；不可注入的会话（WorkBuddy 全系、dsh 待评、APP 形态）输入框禁用并说明原因。已开 TUI 的 Claude/Codex/Kimi 等**优先路由终端注入**（无头 resume 对已开 TUI 会话会分叉出后台续写，开着的界面不实时可见）。
- **边界**：路由表是纯决策件（会话属性 → 通道），不带副作用；ZCode 桌面形态固定路由无头（在册限定，D6）。

### W4 · 移动端发消息（会话详情页）

- **需求**：手机上有自然的多行输入体验，发送后知道「到了哪一步」。
- **输入**：会话详情页输入框（多行，键盘回车=换行，**发送=按钮**）。
- **输出与效果**：
  - 多行归一：发送时换行符替换为字面 `\n`（两个字符）拼接为单行 → 走 W1 单行注入；输入端看起来多行，agent 与大模型按 `\n` 理解换行；**已知限制**：桌面终端与 MAM 详情页不换行展示（字面 `\n` 长串），后续里程碑可升级多行展示；
  - 队列状态指示：排队中（第 N 条）/ 已送达终端 / 失败可重试；
  - 回执语义（定死）：「已送达」= 注入动作成功（终端收到输入）；「agent 已处理」不由回执表达，由状态跃迁/内容流自然体现；
  - 斜杠命令文本原样放行（`/model` 等不拦截不审查），写审计留痕——三期 F3.1 的边界是结构化选择器 UI，不是文本拦截；
  - 授权面 = PIN 配对设备即信任，无额外开关。
- **边界**：不做出站内容过滤（用户对自己设备负责）；单会话发送受 W2 串行约束。

### W5 · 写操作审计

- **需求**：每一次写动作可追溯。
- **输入**：注入 / 队列 / flush / 撤回 / 审批应答 / 无头驱动，逐条。
- **输出与效果**：SQLite 审计表只增不改——设备（id+花名）、时间、目标会话（工具+session_id+项目）、通道、动作、内容摘要（首 N 字符）、结果；桌面设置页提供查看入口。
- **边界**：审计不含全文（摘要即可定位，避免审计库膨胀）；移动端不暴露审计查询（桌面侧能力）。

## 4. 第二部分 · 通道扩展（W6–W8，对应宪法 F2.9/F2.3/F2.4/F2.1 扩展）

### W6 · 审批应答（通道统一，D12 第二层）

- **需求**：会话红·等待批准时，手机上直接批准/拒绝，不用回电脑——**终端会话与无头会话都要能应答**（无头不应答 turn 就卡死）。
- **输入**：审批请求的识别信号——终端会话 = 红卡状态 + 解析器识别审批提示（各家提示形态探测入库）；无头会话 = headless 进程的审批事件（claude `control_request{can_use_tool}`）。
- **输出与效果**：
  - **移动端结构化选项卡是统一 UI**（批准 / 拒绝 / 选项 N / 「不要再问」），机制按通道分派：
    - **终端注入通道（TUI）**：选择后注入对应按键（复用注入引擎，键位而非文本）；**按键映射表：每 CLI 一次探测入库 + 版本探针**——CLI 版本变化提示复核，映射缺失时降级为普通发消息（不发错误键位）；首批 Claude/Codex 只做批准/拒绝，「不要再问」等扩展键位随映射表由简到繁跟进；
    - **无头通道（claude）**：经 `--permission-prompt-tool stdio` 双向控制消息应答（AionCore 实证：claude 发 `control_request` 后阻塞，宿主回 `control_response` allow/deny）——选项卡选择 → 控制消息；
    - **无头通道（codex exec / kimi / opencode）**：无交互审批面 = **审批策略驱动**（spawn 时给定 approval policy，turn 不因审批而阻塞；拒绝/需批准事件回流到回执，用户可调策略后重试）；
  - **watchdog 超时兜底**：无头 turn 超时（默认可配置）自动回收进程并回报超时回执——设计保证「双向应答 / 策略驱动不阻塞 / watchdog」三机制必居其一，**无头 turn 永不静默卡死**。
- **审批边界三档（裁决 13）**：①会话内审批应答属**二期本期**——含工具权限批准（Yes/No/选项/「不要再问」）与**计划模式**的两类操作（发消息继续改计划 = 普通发消息走 M7 注入；点「执行计划」= 批准键注入走 M8）；②权限/模式**主动切换**（计划模式 ↔ 完全访问 ↔ 需人批的设定）属三期 F3.1 切模式，本期不做；③APP 形态会话（WorkBuddy/Codex APP 等）无外部写 API，唯一通路 computer-use/keystroke（需解锁+抢焦点，宪法 D7 应急预案级）→ **本期不做**，登记延后表（附录 C）。
- **边界**：TUI 按键映射首批 Claude/Codex 探测入库（M8），其余工具按探测结论由简到繁跟进；claude 无头双向通道随 M12 无头通道落地（首批预留选项卡→控制消息分派接口）；终端注入为应用级脚本（tmux/AppleScript），**不需解锁也不抢焦点**——锁屏可用性 = M7 实测确认项；协议原生审批通道（app-server/ACP request_permission）属三期 D12 第一层，本期不碰。

### W7 · 无头通道（五家一次做齐 · 里程碑 M12 后移，裁决 11）

- **需求**：未开窗的会话也能被驱动（R2.4）；一次 turn 的结果有回执。**近期需求不强，后移至二期末段（仅先于 APK 套壳）**。
- **输入**：session_id + 文本（多行同样 `\n` 归一，与 W4 统一语义）。
- **输出与效果**：
  - 五家通道：`zcode --resume <id> --prompt <text> --cwd <项目> --json`（**限定在册工作区**，D6 判定 F——桌面刷新后可见）/ `claude -p --resume <session> --output-format stream-json`（配 `--permission-prompt-tool stdio` 承接审批应答，见 W6）/ `codex exec resume <id>`（审批策略驱动，turn 不阻塞）/ `kimi -p -S <id>`（恢复含运行时状态）/ `opencode run`（附 A 矩阵 ✅ 并入）；
  - 进程管理按 **AionCore 骨架**：Spawner trait、进程注册表、空闲挂起、崩溃重生、版本门控；
  - 回执：turn 完成返回末条 assistant 消息 + token 用量；无头产生的新回合经读链路在移动端与桌面 MAM 自然可见；
  - 单会话同时至多一个无头 turn（串行），排队由调用侧约束；审批事件按 W6 分派（claude 双向应答 / 其余策略驱动）+ watchdog 超时兜底。
- **边界**：无头对已开 TUI 的会话默认不路由（W3）；Codex 无头追加后桌面索引不保证刷新（官方 #28259，已知限制明示）；zcode / kimi / opencode 的无头审批与回执行为 = M12 首任务逐家探测确认；OpenClaw 无头（sessions CLI）走后续里程碑，gateway 模式另评。

### W8 · Windows 终端注入（D18）

- **需求**：Windows 实机（mam-win 场景）上的终端会话同样可发消息。
- **输入**：M6 探测里程碑的结论（写入路径定案）。
- **输出与效果**：Windows 终端写入通道（候选：WriteConsoleInput / ConPTY 附加写入 / Windows Terminal 通道，以探测报告为准）；与 macOS 通道同口径的行为（`[mobile]` 标记、`\n` 归一、队列、审计）与同口径验收。
- **边界**：M6 探测报告 + 独立评审先行（类似一期 M0 模式），探测不通过则该里程碑降级登记为已知限制并回报用户裁决。

## 5. 第三部分 · 交接与触达（W9–W12，对应 F2.7/F2.8 + D15/D17 移入项）

### W9 · 会话交接导出（F2.7）

- **需求**：任务可以交接出去——摘要导出人可读、agent 可续；**下一个 Agent 拿到足够信息无缝衔接是第一目标**。
- **输入**：会话卡「交接」按钮；选择摘要档位（规则摘要默认 / LLM 摘要可选）；LLM 摘要时可选**交接模板**（工作类型 × 工作进度，也可不选走默认兜底）。
- **输出与效果**：
  - `~/.mam/handoffs/<时间戳>-<来源>-<目标>-<项目>.md`（HANDOFF v1 九段式：Objective / Work Completed / Current State / Decisions & Rationale / Next Steps / Environment & File Context / Session Log / Smart Defaults / Verification Steps + 原始会话指引）+ SQLite 索引表登记；九段式骨架对所有模板恒定（保持 agent 无关的可续格式），**模板作用于 LLM 摘要提示词与各段内容的侧重**，不增删段落；
  - **交接模板体系（裁决 10）**：`工作类型 × 工作进度` 组合预设——
    - 工作类型（编码 / 设计 / 文档处理 / …）：决定留存偏向——编码类加重代码签名、失败路径、测试期望；设计类加重决策理由与取舍；文档处理类加重结构大纲与口径；
    - 工作进度（任务所处环节，如编码类 = 设计→实现→检查测试）：决定「未完成环节如何接续」的提示侧重——交接价值恰恰在「这一环节没做完，下一个人能否接上」；
    - 组合即针对性提示词（如「编码 × 实现中期」强调已完成清单+未完成清单+失败路径；「编码 × 待测试」强调验证步骤与预期结果）；
  - **默认兜底**：未选择模板时用默认压缩模板（借鉴 Codex checkpoint 口径：当前进展与关键决策 / 重要约束与用户偏好 / 剩余工作清晰下一步 / 关键数据与引用，面向「下一个 LLM 无缝接续」）；
  - 强制保留项（生态实践验证的高价值段，无论模板）：失败路径（「不要重走」）与带预期结果的验证步骤；
  - 规则摘要零依赖离线可用；LLM 摘要复用 W7 无头通道执行（一个摘要 turn）——**无头后移（裁决 11）后：交接导出里程碑（M10）先交付规则摘要 + HANDOFF 格式/索引/入口 + 模板体系定义，LLM 摘要档位随 M12 无头落地**（届时亦可评估「注入自总结」替代：对已开 TUI 发交接指令由 agent 自己写 HANDOFF，.handoff 先例——M10 设计时裁决）；全量 JSON 附本可选随文件落盘。
- **边界**：导出侧 only——ImportService（投递/确认回执）属三期 F3.7；LLM 摘要在无头通道不可用的工具上自动降级规则摘要；**近期只做预设模板，用户自定义模板（设置面板配置交接侧重点）为远期规划不入本期**（裁决 10）。

#### W9.1 · 模板设计依据（2026-09-18 调研落档）

- **各家 compact 提示词现状**（Claude Code / Codex / OpenCode / Amp 一手资料核对）：全部是**单一通用模板**，无一家按工作类型分类；共同保留五要素 = 已完成 / 进行中 / 涉及文件 / 下一步 / 约束与决策——即「默认兜底」的生态基线；
- **可借鉴机制**：Claude Code `/compact <自定义指令>`（用户参数化提示词 = 组合模板的机制接口先例）；Codex 压缩后保留最近用户消息原文（~20k tokens）随摘要并存；OpenCode 的 prune（工具输出分级保留）与 compaction 分离；Amp 的 Handoff 按「下一任务目标」抽取（最接近进度感知）；
- **handoff 实现现状**：社区已成一等公民模式（willseltzer/claude-handoff 插件 / Matt Pocock AI Hero /handoff / beads 集成等）；实证有效的段落实践 = 失败路径清单、代码签名展示（不描述）、带预期结果的测试步骤、原始错误信息——已吸收进强制保留项与九段式。

### W10 · keystroke 应急预案（文档级，F2.8/D7）

- **需求**：万能兜底手段记录在案，不承诺、不默认。
- **输出与效果**：AppleScript keystroke / accessibility 作为应急遥控手段写入文档（适用场景、前置条件、风险：抢焦点/前台要求/中文输入法需切 ABC/自动化权限）；不实现、不暴露 UI。
- **边界**：任何通道失效时的最后手段参考，非正式功能。

### W11 · 推送网关（Bark/ntfy，D17 移入）

- **需求**：页面关着的系统级推送——一期 F1.6 按裁决迁入本期。
- **输入**：状态跃迁事件（SessionWatcher 同源同去重，与 SSE/桌面通知同一套边沿事件）；设置页 Bark/ntfy URL 配置。
- **输出与效果**：**推送网关抽象**（同一事件源多出口）：Bark（iOS）/ ntfy（Android；华为无 GMS 机型默认出口）/ APK 出口（W12 内置长连接）预留；标题=工具+项目，正文=跃迁方向+预览；失败静默重试一次；设置页测试按钮（即华为机到达率实测入口）；默认公共 ntfy 的隐私提示文案随附。
- **边界**：默认关闭按需开启；推送网关不承接写操作回执之外的任何新事件源。

### W12 · APK 壳收尾（D15 触发条件制）

- **需求**：网页链路验收后的原生壳交付。
- **输入**：与网页版完全相同的后端服务。
- **输出与效果**：Capacitor 壳 + **内置长连接推送**（APK 与 MAM 推送网关自有长连接，页面关闭仍收系统通知，通知归属 MAM 自身、点击直达具体会话）+ 前台服务与电池白名单引导页；manualChunks 移动端分包同批（D17 附注）。
- **边界**：纯壳复用无独立功能；**触发条件：M7–M10 发消息能力落地验收通过后方可启动**（D15）；不注册推送厂商账号。

## 7. 非功能需求

- **安全**：PIN 门禁覆盖一切写端点（宪法横切 1）；写审计全覆盖、只增不改；消息标记可归因到设备；注入纯文本语义（不拼 shell 元字符）；单会话串行天然限速；无头/注入通道版本门控+探针+降级（横切 6）。
- **性能**：点发送 → 目标终端出现文字 ≤3s（公网隧道链路）；队列 flush 在静息跃迁后 1s 内；无头回执随 turn 完成返回。
- **可靠性**：注入失败明确回执+可重试；队列 SQLite 持久化重启不丢；无头进程崩溃重生；一期能力零回归（横切 5：桌面监控/通知/资源管理不受影响）。
- **体验**：中文界面与 MAM 一致；回执清晰区分「已送达终端」与（由状态流体现的）「agent 已处理」；不可注入会话明示原因；可见性预期（实时/刷新后）在发送前告知。
