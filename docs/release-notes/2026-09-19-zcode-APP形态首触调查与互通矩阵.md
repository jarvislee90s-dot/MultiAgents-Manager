## 2. 形态判定结论：**APP 类（GUI 主形态），但带一个完整的原生 CLI 面 → 无头可驱动**

### 2.1 判定证据（只读）

| 判据 | 观测 | 含义 |
|---|---|---|
| 进程树祖先 | 主进程 31504 的父是 39484（非 conhost/OpenConsole/WT）；全部 ZCode.exe 由 Electron 拉起 | 非控制台宿主 |
| 可附加控制台 | 主进程无控制台窗口；CLI 会话（`tui`）**根本起不来** | 见下 |
| 窗口类名/框架 | UIA `RootWebArea`（Chromium/Electron），1015 节点，含 1 Edit + 183 Button | GUI 渲染树，非 TUI |
| 终端 TUI 形态 | `zcode tui` → `Error: Cannot find package '@zcode/tui' imported from …zcode.cjs`；全盘无 `@zcode/tui` 目录 | **官方未分发 TUI 包**——`tui` 子命令是死代码 |
| 单实例行为 | `app.requestSingleInstanceLock(argv)`，第二实例经 `--open-workspace` / `zcode://workspace/open?path=` 深链转交首实例 | 无头 CLI 不会另起 GUI；也不改在册清单 |

### 2.2 分流结论

- **Phase 0 分流器命中「无控制台」→ 走 Phase B（APP 类）**。`win-console-inject-probe` 技能
  的边界声明（SKILL.md 第 83 行）把「zcode 桌面形态」明确划在控制台注入工作流之外——本判定与该声明一致。
- **但 zcode 不等于「纯 APP」**：它同时分发一个功能完整的 Node CLI（`zcode.cjs`），
  提供 `-p/--prompt` 无头单发与 `app-server --stdio` 常驻协议服务。二者与桌面**共享同一
  `~/.zcode/cli/db/db.sqlite`**。这决定了 zcode 的正确接入姿态不是「控制台注入」，而是
  「**无头驱动 / 协议通道**」——现行 D6/M11「ZCode 固定走无头」的设计方向是对的（见 §5）。

### 3.2 逐格判据与证据

**a. 无头驱动**：命令形态按 `--help` 实查（非推测）：
```
node "D:\Program Files\ZCode\resources\glm\zcode.cjs" -p "<prompt>" --json [--cwd <dir>]
```
`--json` 让 CLI 输出 `{sessionId, traceId, turnId, response, usage, projection}` 单行 JSON——
**这正是注入引擎需要的「写入确认 + 会话定位」返回**，比控制台注入的截图/文件对账更强。

**b. 落盘核验**：SQLite WAL 库（~870 MB）——**grep 不可用**；对账必须**拷贝 db+wal+shm 三件套
副本**再查（沿 opencode 先例，脚本 `verify-zcode.py`）。查询口径与 MAM 解析器一致（`part` 表
`data` JSON 的 `text` 字段）。
- 反向对照：**未在册目录同样落盘**——落盘不受在册影响。

**b′. tasks-index**：`tasks` 表由 GUI 在「会话创建/发消息」时写入（`task_created` 等事件）；
全库 121 行的 workspace 集合 **100% 落在在册清单内**（`recentProjects ∪ lastWorkspaceSession`），
**零行落在未登记工作区**。但**即使在册，headless 会话也不入此表**——Test 项目 3 个 headless
会话零 tasks 行，而同项目的 GUI 会话 `hi` 有行。**tasks-index 是「GUI 交互」的产物，不是
「会话存在」的索引。**

**c. 有头可见性**（用户前置结论①的现场复验）：
- Test（在册）：侧栏「项目」组下有 `Test`，其下**只有 `hi`（GUI 建）**，今日 headless 建的
  `OK`/`ZCPROBE-TEST-*`/`RESUME-OK` 三个会话**全部不显示** → **复现用户观测**。
- 关键因果：桌面侧栏项目列表读 `~/.zcode/v2/setting.json` 的 `recentProjects[]` /
  `lastWorkspaceSession[]`，该数组**只由 renderer 写入**（GUI 打开目录、关标签持久化时），
  CLI/app-server **无任何写此数组的代码路径**（子代理全盘搜索确认，见 §4 静态证据）。
  → 无头会话「不显示」的根因是**没有 GUI 交互去登记/索引**，而非「无头被禁止」或「未在册」。
  Test2 连 `Test2` 这个项目组都不在设置里，所以桌面上无从显示。

**d. MAM 视角**：`zcode_parser.rs` 出卡条件是 `session.task_type='interactive'` + 24h 窗口 +
`parent_id` 空。**不读** `recentProjects` / `lastWorkspaceSession` / `tasks-index`。
复刻其精确 SQL 对活库查询：**Test2 未在册会话照样出现在结果里**。
→ **MAM 能对未在册会话提供「监控 + 无头驱动」，只是 ZCode 桌面上看不见。** 这是本矩阵
最有价值的一格：它把用户前置结论①的适用范围限定清楚了。

**协议通道要点（复验必读）**：`app-server --stdio` 是 **NDJSON，不是 JSON-RPC**——
消息形如 `{id,method,params}` / `{id,result}` / `{id,error}`，**带 `jsonrpc` 键会被 schema 拒**
（-32600，实测第一次尝试即此结果）。服务端还会反向发 `{id:"server-<n>",method,params}` 请求，
**`session/create` 会阻塞等待客户端回 `session/requestRuntimePreferences`**——不回则 create 永久挂起。
回包 schema：`{nativeSearchEnhancementsEnabled:bool, memoryEnabled?:bool, askUserQuestionAutoResolutionEnabled?:bool, modelContextBudgetStrategy?:"preflight-v1"}`。
（这是本探测踩到的最大坑，记入方法论。）

## 4. 静态证据（bundle 考古，只读）

从 `zcode.cjs`（CLI）与 `app.asar`（桌面）中提取，用于支撑 §3 的因果链。

1. **协议方法表**（CLI `zcode.cjs`，74 个）：`runtime/capabilities`、`session/create|resume|list|read|messages|events|subscribe|send|stop|fork|compact|goal|close|setModel|setThoughtLevel|setMode|subagents`、`workspace/*`、`provider/*`、`mcp/list`、`plugins/*`、`skills/referenceCatalog`、`workflows/*`、`automation/*`、`offPeak/*`、`usage/stats` 等。
   （完整清单见 `%USERPROFILE%\mam-probe-zcode\zcode-protocol-methods.txt`）
   - `session/create` 参：`{workspace:{workspacePath, workspaceKey}, …}`（**workspace 必须是对象**，字符串形态被 Zod 拒）。
   - `session/send` 参：`{sessionId, content, attachments?, expectedRevision?}` → 返 `{accepted, sessionId, stateRevision}`。
   - `session/subscribe` 的 `deliveryKind` 枚举实测为 `desktop-continuous` / `web-remote-replayable`（**不是** `attached`）。
2. **resume 命令表**（CLI `parseArgs`，@char 497457）：`resume:{type:"string"}`、`continue:{short:"c",type:"boolean"}`；
   `--resume` 与 `-c` **互斥**（显式报错）。CLI 侧 `-c` 语义 = 解析「cwd 对应的最新会话」。
3. **在册清单写入方**：`app.asar out/renderer/assets/styles-*.js` 的 open-directory 流程
   `settingService.update({recentProjects:[dir,...]})` 与 tab-persistence `{lastWorkspaceSession:[...]}`——
   **仅在 renderer**。CLI 与 host/scheduler/main 三包全盘搜索无对应写路径。
4. **tasks-index 结构**：`CREATE TABLE tasks(workspace_key TEXT NOT NULL, …, PRIMARY KEY(workspace_key, task_id))`
   （`out/host/chunk-JET77OYC.js`）。写入由 host 的 task 事件族驱动。
5. **单实例**：`out/main/index.js` `requestSingleInstanceLock(gb(process.argv))` + `second-instance` → `handleOpenWorkspacePath`。
6. **桌面侧栏项目源**：`out/host/index.js` `listWorkspaceRefs` 读 `settingService.get()` 的 `lastWorkspaceSession`。

### 5.3 通道优先级建议（本期不实现）

1. **协议通道（`app-server --stdio`）**——能力最全（create/resume/send/subscribe/stop/setMode…），
   返回结构化状态与事件流，无竞态、无焦点需求、无输入形态猜测。**首选**。
2. **CLI 无头 `-p`**——实施成本最低（一次进程），返回结构化 JSON，适合「单发/续跑」。
   缺点：每次起进程（会话创建开销），不适合实时事件订阅。
3. UIA 输入——仅作**应急预案**（D7 级），需抢焦点，本探测未验证。
4. Bot 通道——用户既有外部集成，可作旁路，但**不受 MAM 控制**（属 zcode 侧功能）。

### 5.4 开放问题（如实登记，未测项不补痕迹）

- `--resume` 在**未在册**目录是否同样可用（Test2 未单测；`-c` 已在 Test2 验证可用，语义相近）。
- `--surface` 传 `terminal` 与 `desktop` 的行为差异（`--surface terminal` 未测；`tui` 包缺失可能影响其可用性）。
- 协议通道 `session/subscribe` 的正确 `deliveryKind` 后续用法（枚举已实查，未跑通完整事件流消费）。
- 无头会话是否会在**某次 GUI 交互后**被补登记进 tasks-index（本探测窗口内未见；仅登记现象）。
- 协议通道并发/多客户端语义（`stateRevision` 乐观锁、workspace lease）未测。

## 6. 方法论文摘要（APP 类探测工作流首样本）

可复用于后续 APP 类工具（WorkBuddy、codex APP 等）：

1. **先做形态判定，再分流**——别把 GUI 工具硬套控制台注入流程。判定三件套：进程树祖先、
   UIA/窗口类名、**该工具是否分发独立的 CLI/TUI 面**（zcode 的教训：`tui` 子命令存在但包缺失，
   「命令表」不等于「可用能力」）。
2. **找 CLI 入口看活进程，不要只看安装目录**——`where zcode` 找不到，但活进程命令行暴露了
   `resources/glm/zcode.cjs`。**活进程是安装形态的真相源。**
3. **环境依赖陷阱要挖**——CLI 依赖桌面注入的 provider 环境变量；直接跑失败要先怀疑环境，
   再怀疑工具。静态搜 `process.env[...]` 的必填项最有效。
4. **对照矩阵四格各自独立取证**——「能驱动」「能落盘」「桌面能看」「MAM 能读」是四个独立命题，
   极易被混为一谈（用户前置结论①正是把「桌面不看」误当成「无头不行」）。
5. **SQLite 类库一律副本对账**（db+wal+shm），活库只读不查；grep 不可用。
6. **协议通道探测先发一个最小请求摸协议族**——本次第一次发 JSON-RPC 被 -32600 拒，才确认是
   自定义 NDJSON 信封；再摸到「服务端反向请求必须回包否则 create 挂起」。
7. **红线**：单实例桌面应用绝不全局重启；UIA/输入类探测不抢焦点；证据用 PrintWindow 按窗口抓。
